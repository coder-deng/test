# Deep Agents 学习项目：技术选型调研助手

## 1. 项目目标

通过一个可运行、可逐步扩展的小项目，学习 LangChain `deepagents` 框架的核心用法，而不是一次性堆叠所有功能。

项目采用敏捷迭代：每个 Sprint 都交付一个可以演示和验证的版本，并在复盘后决定下一步。

### 成本硬约束

除大模型调用产生的 Token 费用外，项目的其他部分必须免费：

- 不使用付费搜索 API 或依赖有限免费额度的搜索 API。
- 不使用付费数据库、对象存储、队列或托管服务。
- 不使用可能自动转为按量计费的云端追踪、评估或 Agent 平台。
- 默认在本机运行，使用本地文件持久化。
- 引入新依赖或服务前必须确认许可证、计费方式和是否需要信用卡。

免费额度不等于免费依赖。只要超额后可能自动收费，或核心功能长期依赖有限试用额度，就不能作为默认技术方案。

## 2. 场景定义

### 项目名称

TechScout（技术选型调研助手）

### 用户问题

开发者经常需要在多个技术方案之间做选择，例如：

- “FastAPI 和 Django 哪个更适合小型 AI 服务？”
- “PostgreSQL 的 pgvector 和独立向量数据库该怎么选？”
- “这个项目应该使用 LangChain Agent 还是 Deep Agents？”

普通对话回答容易缺少过程、来源和可复查的产物。TechScout 接收一个技术选型问题，规划调研任务，收集资料，整理证据，并在本地生成一份结构化 Markdown 决策报告。

### 典型使用流程

1. 用户输入调研问题及约束条件。
2. Agent 制订待办计划并逐项执行。
3. Agent 调用搜索工具收集资料，将中间结果保存到工作目录。
4. Agent 对候选方案按统一维度比较。
5. Agent 输出包含结论、权衡、风险和来源的报告。
6. 用户检查报告并提出补充问题或要求重新调研。

### 示例输入

> 我准备做一个 3 人维护的内部 AI API，预计日请求量 1 万，FastAPI 和 Django 应该选哪个？重点比较开发效率、异步能力、生态和维护成本。

### 示例产物

```text
workspace/
└── fastapi-vs-django/
    ├── brief.md
    ├── notes/
    │   ├── fastapi.md
    │   └── django.md
    └── report.md
```

最终 `report.md` 至少包含：

- 问题与约束
- 候选方案
- 比较维度与证据
- 推荐结论及适用条件
- 风险、未知项与后续验证建议
- 信息来源

## 3. 为什么适合学习 Deep Agents

| 框架能力 | 在项目中的落点 |
| --- | --- |
| 规划 / Todo | 把开放式调研问题拆成可追踪步骤 |
| 自定义工具 | 接入网页搜索或其他资料源 |
| 文件系统 | 保存 brief、调研笔记和最终报告 |
| 子代理 | 分别研究候选方案，隔离大量上下文 |
| 上下文管理 | 长调研过程中压缩历史并保留关键证据 |
| 持久化 | 恢复中断的调研会话 |
| Human-in-the-loop | 在高成本搜索或写最终报告前让用户确认 |
| Skills / Memory | 固化调研模板和长期偏好，作为后期扩展 |

第一版只使用最少能力；后续 Sprint 再引入子代理、持久化和人工审批，便于观察每项能力解决了什么问题。

## 4. MVP 边界

### 包含

- Python 命令行应用
- 单个技术选型问题
- 一个 Deep Agent
- 一个搜索工具
- 本地文件工作区
- Markdown 决策报告
- 基本异常提示与运行日志

### 暂不包含

- Web 前端
- 用户账号和权限系统
- 数据库
- 多人协作
- 自动部署
- PDF、图片等复杂输入
- 对报告结论真实性作绝对保证

## 5. 敏捷迭代计划

### Sprint 0：项目骨架与最小闭环

目标：输入问题后，Deep Agent 能调用工具并生成一份本地报告。

待办：

- 初始化 Python 项目和依赖管理
- 配置模型与环境变量示例
- 使用 `create_deep_agent` 创建 Agent
- 实现一个搜索工具
- 编写最小系统提示词
- 提供 CLI 入口
- 用固定问题完成一次端到端验收

验收标准：

- 一条命令可启动应用
- Agent 会展示或维护调研计划
- `workspace/<topic>/report.md` 成功生成
- 报告包含结论、比较、风险和来源
- API Key 不写入仓库

### Sprint 1：结构化过程与可靠输出

目标：让调研过程可检查、失败可理解、输出格式较稳定。

待办：

- 增加调研 brief 模板
- 保存原始来源和方案笔记
- 对来源数量、报告章节做程序化校验
- 增加超时、空结果和模型错误处理
- 为工具和核心流程补充测试

### Sprint 2：多代理调研

目标：引入子代理，学习任务委派和上下文隔离。

待办：

- 为不同候选方案配置研究子代理
- 主 Agent 只负责规划、综合和最终决策
- 对比单代理与多代理的耗时、成本和报告质量
- 限制子代理数量及最大检索轮次

### Sprint 3：持久化与人工控制

目标：让长任务可恢复、关键动作可确认。

待办：

- 接入 Checkpointer，支持按 thread 恢复
- 在高成本检索或最终写入前增加人工审批
- 支持用户补充约束后继续原调研
- 记录基础运行指标和可观测信息

### Sprint 4（可选）：Skills 与长期偏好

目标：把可复用的调研方法从提示词中拆出。

待办：

- 创建“技术选型报告” Skill
- 保存用户偏好的比较维度
- 增加不同报告模板

## 6. 建议技术栈

- Python 3.11+（已确认）
- `deepagents`
- LangChain 兼容、支持工具调用的模型
- `uv` 管理依赖
- 联网搜索：首版使用无需 API Key 的 DDGS；后续可替换为自建 SearXNG 或其他服务
- `pytest` 进行测试
- `ruff` 进行格式与静态检查
- 本地文件系统保存所有项目产物

模型和搜索服务通过环境变量配置，业务代码不绑定某一家供应商。

项目开发语言已确定为 Python，后续不再评估 JavaScript/TypeScript 版本。

项目不启用 LangSmith 云端追踪、付费搜索、云数据库或托管部署；唯一允许产生的第三方使用费是用户主动配置的大模型 Token 费用。

## 7. 学习目标

完成项目后，应能回答：

1. `create_deep_agent` 为普通工具调用 Agent 增加了哪些能力？
2. Agent 的规划、文件系统和自定义工具如何协作？
3. 什么任务值得委派给子代理，什么任务不值得？
4. 如何限制 Agent 的文件、网络、成本和执行权限？
5. 如何检查 Agent 的过程与产物，而不只判断最终文本“看起来不错”？
6. 如何让一次运行可中断、可恢复、可继续？

## 8. Definition of Done

一个 Sprint 只有同时满足以下条件才算完成：

- 功能可通过命令行实际演示
- 至少有一个可重复的验收样例
- 核心路径通过自动化测试或明确的人工验收
- README 或相关文档同步更新
- 不提交密钥、缓存和运行产物
- 除 LLM Token 外没有引入任何付费服务或自动计费路径
- 记录本轮发现的问题及下一轮优先级

## 9. 第一条用户故事

> 作为需要做技术选型的开发者，我希望输入问题和约束后获得一份带来源的 Markdown 比较报告，从而能够复查证据并做出决策。

第一轮编码仅实现这条用户故事，不提前实现 Web UI、多代理或持久化。
